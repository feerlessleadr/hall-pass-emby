# API notes (Phase 0)

Findings from decompiling Emby Server 4.10.1.0 (`MediaBrowser.Controller`, `MediaBrowser.Model`, `MediaBrowser.Common`, `Emby.Providers`, `Emby.Server.Implementations`, `Emby.Api` with `ilspycmd`) and from a hello-world plugin on the test server (2026-10-12). "Checked live" means the plugin ran it against the test server; everything else is from reading code. The design's assumptions lose to these notes. Shared by both tagging plugins (the Tag Team repo has a copy).

## Lyrics and file tags (Hall Pass)

- **Emby exposes lyrics as subtitle streams** on the audio item: an embedded lyric (ID3 USLT or similar) is a `Subtitle` stream with codec `text` and title `Lyrics`; a sidecar `.lrc` is an external `Subtitle` stream with codec `lrc`. Emby can also fetch lyrics itself and save a `.lrc` next to the file (`LibraryOptions.SaveLyricsWithMedia`, default on). So **no extra tag-reading library is needed for lyrics**.
- Reading the text inside a plugin: `IMediaSourceManager.GetStaticMediaSources(item, true, false, null)` for the streams, then `ISubtitleEncoder.GetSubtitles(inputPath, protocol, true, headers, stream, "txt", 0, 0, false, EncodingContext.Static, token)`. **That call returns the path of a converted file in Emby's cache, not the text**: read the file. Checked live on an MP3 with both kinds: the embedded stream gave 1,136 characters over 33 lines, the sidecar 1,547 over 83 lines (the same through `GET /Videos/{id}/{source}/Subtitles/{index}/Stream.txt`, which also works for an admin API key).
- **Emby does not expose arbitrary file tags.** `MediaStream` carries only language, title, comment and the codec fields; `ProviderIds` has MusicBrainz ids (`MusicBrainzTrack` and others) but **no ISRC**, and no iTunes advisory flag. Reading `ITUNESADVISORY`, `rtng` or the MP3 `TSRC` frame needs another route: Emby's bundled ffprobe (`IFfmpegConfiguration.ProbePath`, untested) or a library such as TagLibSharp (untested; would ship as a `.zip`). The survey found advisory flags on only 3 percent of the owner's files, so this is optional for v1; matching online can use artist, title, album and duration instead of an ISRC.
- HTTP calls: `IHttpClient` (`Get`, `GetResponse`, `Post`, `SendAsync` with `HttpRequestOptions`). Not tested.
- Scheduled tasks: `IScheduledTask` (`Name`, `Key`, `Description`, `Category`, `Execute(CancellationToken, IProgress<double>)`, `GetDefaultTriggers()`). Not tested.
- Evidence store (SQLite vs LiteDB vs JSON): not tested. Emby ships its own SQLite wrappers (`SQLitePCL.pretty`, `Emby.Sqlite`); plugins loading their own native SQLite is the fragile option. Test LiteDB (managed) first; JSON lines are enough for a library of a thousand-plus tracks.

## More findings from milestone 3 (tag writing, 2026-10-12)

- **REST quirks:** `GET /Items` returns an item's tags in `TagItems`, but only when `Fields` contains `Tags` (`Fields=TagItems` alone returns nothing, and `Tags` itself is always empty). A list query (`Recursive=true&Limit=...`) is cheap; ask for the tags with `Ids=<comma list>&Fields=Tags,TagItems`. Emby writes a read-only dictionary as a list of key/value pairs: return plain `Dictionary<string, int>` from plugin APIs.
- **Writing:** `ILibraryManager.UpdateItems(items, null, ItemUpdateType.MetadataEdit, true, saveMetadata, null, token)` in batches works (61 tracks in well under a second). `item.SetTags(...)` plus adding `MetadataFields.Tags` to `item.LockedFields` before the update. Items from `GetItemById` are Emby's cached objects: if a job is cancelled or a batch fails before `UpdateItems`, put the in-memory tags and locks back, or the cache and the database disagree.
- **A full refresh with "replace all metadata" kept the tags of locked items** (confirmed again at scale; an unlocked item loses its tag).
- **The plugin page is cached by the browser per plugin version:** Emby builds the page's ETag from the plugin's version, not its content, so a changed page with the same version is not picked up by a browser that already has it. Bump `AssemblyVersion` whenever the page changes (a release does anyway). While testing in the browser pane `location.reload()` did nothing and a hash-only navigation does not reload the app: navigate to a URL with a new query string (`index.html?fresh=N#!/...`).
- **Smart lists (the SmartLists plugin) see the tags,** checked with real collections on 61 tracks (36 likely-clean, 18 explicit-review, 7 explicit): rule `Tags Contains likely-clean` finds 36; `Tags Equal explicit` finds 7 (the whole tag, so not "explicit-review"); **`Tags NotContains explicit` finds 36, so it leaves out both "explicit" and "explicit-review"** (Contains is a substring match). Creating a list through the API needs `UserId` (the owner), even for a collection, when an API key is used; `Order.SortOptions` is required.
- Newer .NET APIs such as `char.IsAsciiLetterOrDigit` do not exist on the plugin's net6.0 target: keep the plugin and `Core` on net6.0 APIs (the tests run on net8.0).

## Online catalogs (checked against the live APIs, 2026-10-12)

- **Deezer by ISRC** (`GET https://api.deezer.com/track/isrc:{ISRC}`, no key): the exact track with `explicit_lyrics` (bool), `explicit_content_lyrics` (0 not explicit, 1 explicit, 2 unknown, 3 edited, 4 partially unknown, 5 not applicable), `duration` (seconds), `isrc`, `artist.name`, `album.title`. Unknown ISRC: HTTP 200 with `{"error":{"type":"DataException","message":"no data","code":800}}`. Quota (about 50 requests per 5 seconds): HTTP 200 with an `error` object, code 4 (also code 100): retry later. **Errors come as HTTP 200**, so the body has to be checked.
- **Deezer search:** the structured query `artist:"x" track:"y"` returned nothing; plain terms (`q=artist title`) work and return live, demo and other versions too, so the answer must be matched by title, artist and length (search results carry no ISRC). Album by barcode works: `GET /album/upc:{upc}`.
- **iTunes lookup by album barcode** (`GET https://itunes.apple.com/lookup?upc={upc}&entity=song`, no key): the album plus each song with `trackExplicitness` (`explicit`, `cleaned`, `notExplicit`), `trackTimeMillis`, `trackName`, `artistName`: one request covers a whole album. About 20 requests a minute are allowed. iTunes search (by words) returns covers, karaoke and live versions first and no ISRC: not used.
- **Flags are unreliable for older songs:** the same track can be explicit on Deezer's album and not on the track, and iTunes called several clearly profane Rage Against the Machine tracks `notExplicit`. So an online "not explicit" is capped below the automatic clean bar (0.85) and only counts as clean together with a second source (lyrics or another catalog). "Explicit" from a catalog is taken seriously.
- **ISRC and album barcode live in the file's tags** and Emby does not expose them: Hall Pass runs Emby's own ffprobe (`IFfmpegManager.FfmpegConfiguration.ProbePath`, injected into the plugin) with `-show_entries format_tags:stream_tags -of json`, about 50 ms a file. MP3 stores the ISRC in `TSRC` (ffprobe shows it as `tsrc`), FLAC in `ISRC`; the barcode is `barcode`, `upc` or `ean`. For MP4/M4A the advisory atom `rtng` is searched for in the first and last 8 MB of the file because ffprobe may not show it.
